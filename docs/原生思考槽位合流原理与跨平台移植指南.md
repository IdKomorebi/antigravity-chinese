# Antigravity CLI 原生思考槽位合流原理与跨平台移植指南

本文档阐述 `antigravity-chinese` 的底层渲染改造原理、双平台（macOS ARM64 & Linux `x86_64`）机器码补丁细节，以及利用 Go `.gopclntab` 函数符号表向 Windows (`agy.exe`) 或后续新版本移植的标准方法。

---

## 一、 底层痛点根因

通过对 Antigravity CLI (`agy`，Go + BubbleTea 架构) 的符号表（`.gopclntab`）、渲染状态机（`jetski/cli/render`）及真实会话日志（`transcript.jsonl`）逆向分析，原生客户端在中文环境下存在三大结构性痛点：

### 1. 云端 Summarized Thinking 的强制英文漂移（Gemini & Claude 共有）
- **Google Gemini 系列**：客户端返回的 `thinking` 字段并非模型原始推理流，而是经云端二级 **Thought Summarizer** 提炼后的第三人称摘要。一旦模型内部 `<thought>` 涉及英文代码符号、文件路径或系统提示词，云端摘要器便会将整段思考摘要重写为英文。
- **Anthropic Claude 系列**：Anthropic API 默认启用服务端 Summarized Thinking（同样经常输出英文摘要），且在连续发起工具调用的步骤中常返回空 `thinking=""`、仅在 `content` 字段输出说明文本。
- **传统提示词法的局限**：若通过规则强行限制模型内部 `<thought>` 只能写简短纯中文、禁写代码和英文符号，会直接压缩模型在复杂调试与逆向工程中的推理深度。

### 2. 折叠态单行 `...` 省略号腰斩
在 `jetski/cli/render/render.stepContent` 与 `collapsedThinkingSnippet` 中，默认未展开（未按 `Ctrl+O`）状态下渲染器仅截取思考文本的最后一个段落，并调用 `fitDetailText` 按单行宽度硬性截断为 `...`；工具里程碑汇总 `semanticMilestoneLines`（`○ Thought for Xs (...)`）同样调用了 `fitDetailText` 单行截断。

### 3. Glamour Markdown 中文右边缘吞字
`agy` 使用 `charmbracelet/glamour` + `go-runewidth` 计算终端折行宽度。当正文包含中文弯引号（`“` `”`，Unicode 东亚模糊宽度字符）或引用块与英文混排时，列宽计算偏差会导致行尾超出视口右边界 1~2 列，引发吞字或竖线错位。

## 二、 原生思考槽位合流架构（Native Thought Slot Fusion）

本方案采用 **“内部满血推理 + 客户端渲染槽位合流”** 架构，在不损失任何推理能力的前提下实现 100% 原生中文思考体验：

1. **推理与呈现完全解耦**：模型内部 `<thought>` 保持 100% 自由深度推演；全局规则 `GEMINI_ZH_BEST_PRACTICES.md` 仅要求模型在发起工具调用时，同步在伴随文本（`Response`）中自然浓缩 1~2 句（`<= 640` 字节）中文思考摘要。
2. **机器码级槽位合流**：直接修补客户端 `render.stepContent` 入口机器码——当检测到步骤处于**工具调用态**（`ToolCalls.len > 0`）或**流式生成未完成态**（`step.Status != 3`）且伴随文本长度在 `(0, 640]` 字节内时，直接将思考文本指针重定向至该中文摘要，并写入专用负值合流标记 `-1`。
3. **流式稳定锚定与重复正文抑制**：修正折叠块第二行条件跳转（将“仅等于 0 渲染”放宽为“`<= 0` 均渲染”），使流式首字起即稳定显示在 `▸ Thought for Xs, Y tokens` 正下方的原生浅灰缩进槽内；同时在进入下方 `renderPlannerBody` 前拦截负值标记 `-1`，自动跳过下方重复的白字正文渲染。
4. **全链路反截断**：移除 `collapsedThinkingSnippet` 的末段裁剪以及各思考分支对 `fitDetailText` 的单行截断调用，交由外层容器按终端实际宽度自适应软折行。

## 三、 双平台十处核心二进制补丁详解

### 1. macOS Apple Silicon (`arm64` Mach-O, `agy v1.5.4`)

Mach-O `__TEXT` 段虚拟基址为 `0x100000000`，文件偏移满足 `FileOffset = VA - 0x100000000`；修改后需执行 `codesign -f -s -` 重建 Ad-hoc 签名以通过 Apple Silicon 内核校验。

| 序号 | 文件偏移 | 大小 | 所属函数 | 机器码改造说明 |
| :---: | :--- | :---: | :--- | :--- |
| 1 | `0x02bb0560` | 32B | `glamour.WithWordWrap.func1` | 利用尾部对齐区植入 `if width > 20 { width -= 4 }`，预留 4 列安全右边距 |
| 2 | `0x02c78624` | 100B | `render.stepContent` | 当 `0 < Response.len <= 640` 且 (`ToolCalls.len > 0` 或 `Status != 3`) 时，将 `(x9, x10)` 指向中文 `Response` 并置 `x8 = -1` |
| 3 | `0x02c78fe8` | 12B | `render.stepContent` | 将 `cbz x2, 0x102c79050` 改写为 `ldr x2, [x27, #0x5010]; cmp x2, #0; b.le`，使 `x8 = -1` 正常渲染第二行浅灰摘要 |
| 4 | `0x02c78b18` | 4B | `render.stepContent` | 将 `verbosity == "low"` 分支的 `cbz x8` 改为无条件跳转 `b`，保留已合流思考块 |
| 5 | `0x02c78a94` | 8B | `render.stepContent` | 流式分支进入正文渲染前执行 `bic x8, x8, x8, asr #63`，当 `x8 == -1` 时清零以抑制下方重复白字 |
| 6 | `0x02c79b70` | 8B | `render.stepContent` | 完成态分支进入正文渲染前同样执行 `bic x8, x8, x8, asr #63` 抑制重复白字 |
| 7 | `0x02c7558c` | 4B | `render.collapsedThinkingSnippet` | 将段落裁剪跳转改为无条件 `b`，完整保留多段中文思考 |
| 8 | `0x02c755d4` | 4B | `render.collapsedThinkingSnippet` | 将 `bl fitDetailText` 替换为 `nop`，废除折叠槽单行 `...` 截断 |
| 9 | `0x02c64c80` | 4B | `render.semanticMilestoneLines` | 将分支 1 的 `bl fitDetailText` 替换为 `nop` |
| 10 | `0x02c64e58` | 4B | `render.semanticMilestoneLines` | 将分支 2 的 `bl fitDetailText` 替换为 `nop` |

| 序号 | 文件偏移 (`v1.5.11`) | 大小 | 所属函数 | 机器码改造说明 |

| 3 | `0x0a7e7e47` | 2B | `render.stepContent` | 将 `je` (`74 5c`) 升级为 `jle` (`7e 5c`)，确保 `%r10 == -1` 渲染浅灰第二行摘要 |

## 四、 Go `.gopclntab` 符号定位与 Windows / 新版本移植原理

尽管官方发布的 `agy` / `agy.exe` 剥离了常规操作系统符号表（`nm` 无输出），但作为 Go 1.22+ 编译产物，其二进制内部必然包含 `.gopclntab`（或 PE 中的只读数据节内嵌 `0xfffffff1` 魔数头），完整记录了所有 Go 函数的精确入口地址与函数名：

1. **解析 `.gopclntab` 头**：搜索魔数 `\xf1\xff\xff\xff\x00\x00`（小端 `0xfffffff1`，量子宽度 `1` 或 `4`，指针大小 `8`），读取 `nfunc`、`textStart`、`funcnameOffset` 与 `pclnOffset` 即可精确提取以下 5 个目标函数的起止虚拟地址：
   - `github.com/charmbracelet/glamour.WithWordWrap.func1`
   - `jetski/cli/render/render.stepContent`
   - `jetski/cli/render/render.collapsedThinkingSnippet`
   - `jetski/cli/render/render.semanticMilestoneLines`
   - `jetski/cli/render/render.fitDetailText`
2. **Windows PE (`x86_64`) 的天然同构优势**：
   Go 在 `amd64` 架构上使用自有的 **Go Internal ABI**（寄存器传参顺序固定为 `RAX, RBX, RCX, RDI, RSI, R8, R9, R10, R11`，不随 Linux SysV 或 Windows x64 C ABI 改变）。因此，Windows `agy.exe` 上述 5 个函数的 `x86_64` 机器码结构与 Linux `x86_64` 几乎完全一致，唯一区别仅在于 PE 节表的地址换算：
   - 先由 PE Optional Header 读取 `ImageBase`（通常为 `0x400000` 或 `0x140000000`）；
   - 计算 `RVA = VA - ImageBase`；
   - 在对应的 Section Header（`.text` 或 `.rdata`）中按 `FileOffset = RVA - VirtualAddress + PointerToRawData` 换算为文件字节偏移即可。
